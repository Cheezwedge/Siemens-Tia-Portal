# S7-1200 G2 and TIA Portal V21 specifics

What is different about your hardware and version, and where the toolchain needs a
value only you can look up.

---

## 1. The G2 is a new generation, not a new firmware

The **S7-1200 G2** is a second generation of the S7-1200 family with new hardware,
new order numbers, and a firmware line that starts again at **V1.x** (V1.0, V1.0.1,
V1.1 …). It is not a firmware update to a classic S7-1200 and the two are not
interchangeable in a project.

Practical consequences:

- **Order numbers differ.** The G2 CPUs use a `-...5x-...` type group where the
  classic parts used `-...4x-` or `-...3x-`. For example the G2 CPU 1214C DC/DC/DC
  is **`6ES7214-1AH50-0XB0`**, where the classic equivalent was `6ES7214-1AG40-0XB0`.
  Pasting a classic MLFB into a G2 spec produces a classic CPU that then rejects your
  hardware.
- **Modules are their own family.** G2 signal modules and boards are not the classic
  SM/SB catalogue. Do not assume a classic module MLFB works.
- **Firmware is V1.x.** In the type identifier that is
  `OrderNumber:6ES7 214-1AH50-0XB0/V1.1` - not `/V4.x`, which belongs to the
  classic line.
- **You need V20 or newer**, and V21 for the current firmware and feature set. If a
  G2 CPU does not appear in your catalog at all, you are missing a Hardware Support
  Package (HSP) - install it via *Options ▸ Support packages*.

### Where to get the exact strings

**I could not verify G2 module order numbers from a source I trust, so the toolchain
does not ship a catalogue of them.** Instead:

1. In TIA Portal V21, open the project's hardware catalog.
2. Navigate to the device, select the exact variant.
3. The information pane shows the **order number** and the available **firmware
   versions**. Copy both, character for character, into the spec.

That is a 20-second lookup that removes all guesswork. The example spec
`spec/examples/conveyor-line.yaml` deliberately carries the literal placeholder
`REPLACE-WITH-CATALOG-MLFB` for its analog-output module, and `tiagen validate`
warns about it until you replace it:

```
WARNING module AQ_Module: 'REPLACE-WITH-CATALOG-MLFB' does not look like a Siemens
        MLFB. Openness matches the catalog string exactly - copy it from the
        hardware catalog.
```

The CPU MLFB in the examples (`6ES7214-1AH50-0XB0`, CPU 1214C DC/DC/DC G2) is taken
from a distributor listing and matches Siemens' own G2 documentation; verify it
against your own part before you order anything.

## 2. On-board I/O of the CPU 1214C G2

| | Count | Default addresses |
|---|---|---|
| Digital inputs | 14 | `%I0.0` … `%I1.5` |
| Digital outputs | 10 | `%Q0.0` … `%Q1.1` |
| Analog inputs | 2 | `%IW64`, `%IW66` |
| Analog outputs | **0** | - |

Two things follow, and both are baked into the generator's defaults
(`io.di_start_byte: 0`, `io.ai_start_byte: 64`):

- **Any analog output needs a module or signal board.** The `vfd_analog` equipment
  type therefore usually needs a `plc.modules` entry, and its `speed_out` address
  must match whatever TIA assigns that module in the device view. Set it explicitly:

  ```yaml
  - name: FillPump
    type: vfd_analog
    signals:
      speed_out: "%QW80"
  ```

- **The generator does not know how much I/O you have.** It allocates from byte 0
  upwards and reports the highest address used in `out/*/report.md`:

  ```
  Highest address used per area:
  - Inputs: `%I1.5`
  - Outputs: `%Q1.0`
  ```

  Compare that against the table above. If the report shows `%I2.3` and you have no
  input module, TIA will reject the tag at compile time - which is the right place to
  find out, but the report finds out sooner.

## 3. Openness on V21

### V21 breaks compatibility, on purpose

An Openness application built against V20 or earlier **does not run against V21**.
There is no shim. You recompile against the V21 assemblies, and if you use Siemens'
resolver package you need version **2.x** (`.NET Framework 4.8`, V21+); the 1.x line
covers earlier versions.

Keep the version out of your source. The `.csproj` here takes it as a property:

```bat
msbuild TiaGen.Openness.csproj /p:Configuration=Release ^
        /p:TiaOpennessDir="C:\Program Files\Siemens\Automation\Portal V21\PublicAPI\V21"
```

### What V21 adds that matters for code generation

- **SIMATIC Source Documents** (`.s7dcl` + `.s7res`) - text export/import covering
  LAD, FBD, SCL, DBs, PLC data types and mixed-language blocks. This is the feature
  that makes git-based review of PLC code practical. Available from V20, and the
  centre of V21's CI/CD story. See
  [03-simaticml-and-source-formats.md](03-simaticml-and-source-formats.md).
- **Modern HMI engineering** for panels, PCs and Industrial Edge, with Unified as
  the default runtime.
- **SiVArc V21** gains Unified Edge RT generation and additional Openness APIs -
  relevant if you outgrow the screen plan this toolchain emits and want full
  automatic screen generation.

### The environment checklist

Run this before anything else; it checks all of it:

```bat
TiaGen.Openness.exe doctor
```

- x64 process (the Siemens assemblies are x64-only)
- .NET Framework 4.8
- membership of the local group **`Siemens TIA Openness`**
- Openness assemblies registered under
  `HKLM\SOFTWARE\Siemens\Automation\Openness`

## 4. Programming-language support on the S7-1200

Worth knowing before you plan a code generator around it:

- **LAD, FBD and SCL** are available for the S7-1200. This toolchain generates SCL,
  which is why it works on a Basic controller.
- **GRAPH and STL are not** available on the S7-1200. If you want a sequencer, write
  it as an SCL state machine - which is what the `AUTO SEQUENCE` region in the
  generated machine FB is for.
- **Optimized block access** is the default and what the generated blocks declare
  (`{ S7_Optimized_Access := 'TRUE' }`). It is also what lets the HMI bind
  symbolically to instance-DB members such as
  `DB_BottleLine.InfeedConveyor.Hmi.Sts_Running`.

## 5. Things to check on a G2 project that bite later

- **Protection and access levels.** The G2 security model is stricter than the
  classic line. If a download is refused, the access level and the configured
  password are the first place to look, not the network.
- **OPC UA** needs a licence/runtime setting and the right firmware; it is not on by
  default.
- **PROFINET device names** are derived from the station name unless you set them.
  The driver sets them from `profinet_name` in the plan, defaulting to the
  lower-cased device name with underscores turned into hyphens - which is what the
  device on the wire will need to match.
- **Firmware in the project vs on the CPU.** A mismatch surfaces as a download
  error, not a configuration error. Set `plc.firmware` to what the CPU actually runs.
